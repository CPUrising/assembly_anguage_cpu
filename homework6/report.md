# 作业 6（输出日历）实现报告

## 一、任务与实现方案

- 任务：输入年份（1900~2099）和月份（1~12），输出对应月历。
- 实现：`calendar.asm`（8086 汇编，MASM 5.0 + DOSBox）；C 语言对照见 `calendar.c`。
- 汇编程序结构：
  - `CODESEG2`：功能过程段（`READ_NUM`、`PRINT_STR`、`PRINT_CHAR`、`PRINT_YEAR`、`PRINT_NUM2`、`CALC_MONTH_DAYS`、`CALC_FIRST_DAY`、`PRINT_CALENDAR`）
  - `CODESEG1`：主程序段，通过 `CALL FAR` 调用过程段，形成段间调用
- 三种参数传递方式都做了对照：寄存器（`READ_NUM`/`PRINT_NUM2`）、数据段（`CALC_MONTH_DAYS`/`PRINT_CALENDAR`）、堆栈（`CALC_FIRST_DAY` + `RET 4`）。

## 二、遇到的困难、挫折与纠正

### 1. 自动化编译一开始"看起来成功，实际什么都没编译"

- 现象：DOSBox 启动后返回成功，但目录里没有 `.OBJ`，`MASM.LOG` 是 0 字节。
- 原因：命令写成 `masm calendar.asm > masm.log`，MASM 5.0 会继续询问 `Object filename`，而 DOSBox 的 `-c` 没有交互输入，程序就停在那里。（据此更新README）
- 纠正：改用 `masm calendar.asm;`（分号表示后续提示全部取默认值）；链接同样用 `link calendar.obj;`。之后日志才真正出现内容。
- 附带教训：PowerShell 的 `&` 不会等待 GUI 程序，需要 `Start-Sleep` 或确认进程结束后再读产物，否则会误判为"没生成文件"。

### 2. 第一次汇编：10 个 Severe Error

第一次编译的日志（`masm.log`）：

| 错误 | 行号 | 原因 | 纠正 |
| --- | --- | --- | --- |
| `A2050: Value out of range` | 50 | `ACC_TAB` 用 `DB` 存放累计天数，但 11、12 月前的累计天数是 304、334，超过 255 | 改为 `DW`，同时访问时下标乘 2 |
| `A2071: Forward needs override or FAR` | 70~110 | 主程序段在过程段之前，`CALL` 引用的是后面才定义的 FAR 过程，汇编器无法确定调用类型 | 把过程段整体挪到主程序段之前，使所有 `CALL` 都变为向后引用 |
| `A4031: Operand types must match` | 363 | `MOV BX, MONTH` 用 16 位寄存器取字节变量 | 改为 `MOV BL, MONTH` + `XOR BH, BH` |

### 3. 第二次汇编：EXTRN 方案失败，绕了一圈才回到正确做法

- 为修 `A2071`，第一反应是在主程序段加 `EXTRN ...:FAR`、在过程段加 `PUBLIC`。
- 结果反而报了 14 个错误：`A2073: Symbol is already external`、`A2015: Symbol already different kind`、`A2000: Block nesting error`。
- 原因：这些过程本来就在同一个模块里，`EXTRN` 声明为外部符号后，再在模块内定义就冲突了。
- 纠正：撤掉 `EXTRN`/`PUBLIC`，直接调整段的顺序（过程段在前、主程序段在后），一次通过，0 Warning / 0 Severe Error。

### 4. 段间调用的栈参数偏移算错，星期整体错位

- 现象：`2026-11` 的第一行输出前面多了 2 个空格，即 11 月 1 日被当成了星期二。
- 排查：临时在 `MOV FIRST_DAY, AL` 后插入打印语句，把 `FIRST_DAY` 直接输出，确认它确实是 2 而不是 0。
- 原因：`CALC_FIRST_DAY` 里按"段内调用"的习惯写了 `[BP+4]`、`[BP+6]`。但段间调用的返回地址是 **4 字节（IP + CS）**，参数实际在 `[BP+6]`、`[BP+8]`；`[BP+4]` 取到的是返回的 CS，`[BP+6]` 取到的是月份，于是年份、月份全错。
- 纠正：改为 `[BP+8] = 年`、`[BP+6] = 月`，并在过程注释里写明"段间调用压入 4 字节返回地址"。

### 5. 前导空格只补了 1 格，表头与日期不对齐

- 现象：`2026-11` 的 1 日和表头 `Su` 对不上。
- 原因：每个日期格占 3 列（"%2d " 的效果），但前导空位循环里每个空位只输出 1 个空格。
- 纠正：每个空位输出 3 个空格。修正后 `2026-11` 从周日开始、`1900-01` 从周一开始，均与表头对齐。

### 6. 1900~2099 累计天数超过 16 位，2099 年 12 月算错

- 现象：`2099-12` 输出成周日开头，而实际 2099-12-01 是星期二；`2026`、`2000`、`2024` 等年份却都正确。
- 原因（最隐蔽的一个）：从 1900-01-01 到 2099-12-01 共 73018 天，超过 65535。原代码先把总天数累加在 `SI` 里再统一 `DIV 7`，`SI` 已经回绕，余数自然错。年份越大越晚暴露，属于典型的"边界数据才出错"。
- 纠正：既然只关心"对 7 取余"，就在每一步累加后立刻取模（`DIV 7` 取 `DX`），使中间值始终小于 400；闰年数改用 `SHR AX,1` 两次代替除法，也顺带释放了寄存器。
- 复验：`2099-12` 现在正确输出为周二开头。

### 7. 验证脚本的一个小插曲

- 现象：一次 DOSBox 会话里连续跑 6 组输入，前 5 组都生成了 `OUTn.TXT`，第 6 组（非法输入 `1899 / 13`）没有输出文件。
- 处理：单独起一次 DOSBox 只跑这一组，得到 `Invalid input!`，功能本身没问题；判断是多条 `-c` 连跑时最后一条未被执行的环境问题，未再深究。
- 教训：批量验证要保留"单项复验"这一步，不能因为脚本没产物就认定程序有 bug。

## 四、体会

1. **段间调用与段内调用的差异不只是 CALL 的机器码**：返回地址从 2 字节变成 4 字节，`[BP+n]` 的偏移、`RET`/`RETF`、参数清理都要跟着变。这次第 4 个问题就是最直接的教训。
2. **条件跳转只有 short（位移 1 字节，±127）**：代码变长后，条件跳转目标可能超范围，需要 `Jcc` 跳到附近标签再用 `JMP`（near，位移 16 位）接力；跨段则必须用 `JMP FAR`/`CALL FAR`。代码里 `PC_END` 处就保留了这个写法示例。
3. **16 位寄存器的边界比想象中容易踩**：1900~2099 的累计天数、累计天数表都越界过。写 8086 程序要主动估算最大值，必要时提前取模或改用 32 位运算。
4. **自动化验证要看到"真产物"**：日志 0 字节、缺少 `OUT6.TXT` 这类现象，先怀疑验证脚本，再怀疑程序。用临时打印把中间变量（`FIRST_DAY`）打出来，比盯代码猜要快得多。
